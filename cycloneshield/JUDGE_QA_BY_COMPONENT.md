# CycloneShield: Judge Q&A by Demo Component

Use this as a rehearsal card after the five-minute pitch. The answers below are intentionally candid: a strong technical answer distinguishes **live service data**, **historical/cached source data**, **configured prototype data**, **screening estimates**, and **synthetic training data**. Never upgrade one category verbally to another.

## The five data labels to keep straight

| Label | Meaning in this prototype | Example |
|---|---|---|
| **Live feed** | A request is made to an external service during the current app run and the app visibly reports a live response. | Open-Meteo forecast/weather or marine API when its status says **LIVE**; a Gemini Vision result only when the UI confirms that specific response. |
| **Historical source data** | Source data describe past events, even if they originally came from a real public data provider. | NOAA IBTrACS historical cyclone observations. |
| **Bundled/cache data** | Data are stored with or cached by the app and used without a live query. | `data/noaa_sample_tracks.json`, local district GeoJSON, OSM baseline GeoJSON, sample damage images. |
| **Configured/screening estimate** | Values are generated by app rules or simplified physical assumptions for a scenario. | District risk score/counts, pressure-based surge, illustrative inundation zones, state-specific what-if profiles. |
| **Synthetic training data** | Artificial examples created from defined relationships, not observed event outcomes. | The lifeline ML training set and its evaluation metrics. |

**Important:** A real public data source can be served from a local cache. “Source is NOAA/OSM/SRTM” does not mean “this value was fetched live just now.” For live APIs, point to the visible status badge and retrieval time.

## Questions likely to be asked at any point

### “Is this a working product or a slideware concept?”

“The Streamlit application is interactive and the key workflows run: state/scenario selection, map and district views, broadcast formatting, file export, photo triage path, simulator, and optional live meteorology. Some integrations have offline fallbacks, and some risk values are configured screening data. I distinguish those modes on screen rather than calling every result live.”

### “Which parts are real data?”

“NOAA IBTrACS is a real historical cyclone archive; the app may use its bundled local sample catalog instead of querying BigQuery. The district boundaries and OSM-derived baseline are local files. Open-Meteo can provide live weather if the badge says LIVE. The risk matrix and many facility-impact counts are deterministic configured scenario estimates; the ML training examples are synthetic.”

### “Which parts are live right now?”

“The UI is live. Open-Meteo is live only when this panel says LIVE and shows a retrieval time. Gemini is live only when this specific triage request confirms a live Gemini response. BigQuery is live only if the pipeline reports a successful connection/query. A configured key or a code integration alone is not proof.”

### “What happens when I select West Bengal? Does it fetch new data?”

“It switches the app to the West Bengal entries already configured locally: the cyclone choices, the matching district records available in the bundled GeoJSON or in-code fallback profile, the regional-language default, and the state-specific simulator profile. It does not automatically fetch fresh state-agency data or create an authenticated connection to West Bengal’s control room.”

### “How does it scale from West Bengal to four other states?”

“The prototype has five state configurations and shared components. A production rollout would make the state differences data/configuration packages: authoritative boundaries, current hospitals/shelters/roads, local forecast and gauge feeds, approved language templates, escalation thresholds, and alert integrations. We would onboard one state, validate it with that agency, version the configuration, and only then replicate the integration pattern.”

### “Are you protecting 188 million people today?”

“No. Over 188 million is the cited Census 2011-era coastal-district population scale of the problem. It is not active users, deployed coverage, or a measured impact from this prototype.”

### “Can officials use this as an official forecast or evacuation order?”

“No. This is a decision-support prototype and screening workflow, not an IMD forecast or an authorized evacuation system. A designated agency must validate data and approve any public-facing action.”

### “Where is this deployed?”

“The public URL used for this demo was on Streamlit Community Cloud. The repository contains Docker and Cloud Run deployment assets, but those assets are not evidence that this URL is currently hosted on Cloud Run. Vertex AI is also a packaging/deployment blueprint; inference in the current simulator runs locally.”

## Opening situation card and selectors

### “Does ‘Citizens at Risk’ mean that many people are confirmed to be affected?”

“No. It is the sum of the configured district population references for the selected state scenario. It is a planning-scale indicator, not a real-time exposure count, evacuation registry, or confirmed affected-population estimate.”

### “How are the headline road, hospital, shelter, and evacuation KPIs calculated?”

“They summarize the current deterministic district-risk rows. Counts and road lengths are scenario values assigned by the prototype's rules; they are not observations from a live emergency operations center.”

### “If I change the state, what updates?”

“The app reruns with the selected state's local storm options, its district records or fallback list, its scenario-based risk rows, the state-specific simulator profile, and regional-language default. It does not download or authenticate to new state feeds.”

### “Can I upload a live IMD bulletin?”

“The custom-track control can parse a user-uploaded CSV with `time`, `lat`, `lon`, `wind_kts`, and `pressure_mb` fields. An operator must obtain the bulletin and upload it. The sample bulletin button is hard-coded demonstration data; it is not connected to IMD, so check the values/date and never present it as a current warning.”

## Tab 1 map layers and inspector

### “What do the five map-layer choices mean?”

“District Risk places configured district markers; Severed Highways draws schematic corridor segments between district points; Coastal Surge draws illustrative circles; Wind Swaths draws fixed-radius rings around the display landfall point; Cyclone Track plots the selected cached track when available. These are visualization layers, not five independent live geospatial analyses.”

### “Are the red road lines exact road geometries?”

“No. The highway view draws schematic connections between district coordinates and colors them from scenario risk values. It is not a routing graph, a current traffic layer, or surveyed road-segment inundation.”

### “Does selecting a different inspector district refresh the storm forecast?”

“No. It changes which configured district row is displayed and emphasized on the map and supplies values to the templated broadcast. It does not fetch a new district-specific storm track.”

### “Where are the hospital and shelter counts from?”

“In this display, they are generated by deterministic scenario rules, not live asset-by-asset geospatial intersection. A deployment must replace or reconcile them against state-verified assets and apply a validated hazard overlay.”

“The selected state filters the bundled coastal district GeoJSON when that state is represented there; the app has an in-code fallback district profile as well. ## Tab 1 — Situation & Hazard Maps / District Inspector

### “What does the map show?”

“It is a Folium map with OpenStreetMap and Esri imagery basemaps and scenario overlays for configured district risk, highway corridors, surge circles, wind-radius rings, or the selected historical track. It is not a live satellite image of the cyclone, and the circles/lines are simplified map representations.”

### “Are the road cut-offs and hospital numbers computed from actual geospatial overlays?”

“Not in the displayed dashboard risk matrix. The app's district vulnerability function assigns risk tiers and example facility/road counts using deterministic rank-based rules and storm intensity. A separate infrastructure module contains spatial-join logic and an OSM-derived baseline, but we should not describe these displayed dashboard counts as a fresh live facility-by-facility overlay.”

### “Why show hospitals, shelters, and substations if the counts are illustrative?”

“They demonstrate the intended lifeline decision workflow and output schema. Before operational use, each count and location must be replaced or reconciled with authoritative, state-maintained asset inventories, with confidence and last-updated metadata.”

### “How is the risk score calculated?”

“In this dashboard path, scores and tiers use deterministic rules based on the selected state's district ordering and selected storm wind/surge inputs. They are not a validated probability of harm. The separate what-if tab is the scikit-learn probability model, also still at screening stage.”

### “What does the landfall point mean?”

“For a cached track, the map chooses a point from that track near the selected state's reference coordinates as a display proxy. If track points are unavailable, the map can use a state-centre/default coordinate. It is not an independently issued landfall forecast.”

### “Is the surge forecast real?”

“The headline surge value is an inverted-barometer/pressure-deficit screening proxy. The inundation display is simplified, and full hydrodynamic validation is a roadmap item. OpenTopodata SRTM elevations can be queried by a separate module; that does not make the displayed surge a SLOSH/ADCIRC forecast.”

### “Does the inspector actually call Gemini?”

“No—not for the current displayed district score/directive. The inspector reads the selected scenario's risk row and deterministic action text. Gemini advisory-generation code exists elsewhere in the repository, but this dashboard panel does not invoke it.”

## Tab 2 — Voice Alerts & Broadcast Hub

### “Is the alert written by Gemini?”

“The dashboard's current broadcast text comes from fixed multilingual templates populated with the selected district and scenario values. It is not a live Gemini translation or a live call to Google Cloud Translation.”

### “Are all seven languages ready for public safety use?”

“The interface and template paths cover seven languages, but technical language coverage is not safety certification. Each message needs native-speaker and agency review, especially place names, evacuation instructions, emergency numbers, and low-literacy comprehension.”

### “Does SMS or WhatsApp actually get sent?”

“No. The app creates copy-ready text. It has no connected SMS gateway or WhatsApp Business delivery integration in this demo.”

### “Is the SMS guaranteed to fit every carrier's 160-character limit?”

“The template truncates text at 160 Python characters. Actual SMS encoding and carrier segmentation can differ, especially for non-Latin scripts and Unicode. Before production, validate encoding, segmentation, language, sender ID, and delivery acknowledgements against the selected gateway.”

### “Does downloading CAP XML alert the public or connect to SACHET?”

“No. It creates a CAP-formatted XML file for review or future integration. There is no verified SACHET, Doordarshan, telecom cell-broadcast, or public-send integration in this demo. The agency needs to validate the payload schema, approval workflow, and receiving gateway.”

### “Is the Bengali/Tamil audio generated by Cloud TTS?”

“The voice engine attempts Google Cloud Text-to-Speech when its credentials are configured, and has other network/offline fallback paths. I identify it as Cloud TTS only if the synthesis tier for this audio has been verified. A playable audio file alone does not prove which tier produced it.”

### “What happens if the cell network fails?”

“The prototype can prepare a radio/public-address script and synthesize audio where a voice tier works. It does not operate a radio transmitter or guarantee radio delivery. A production design would export audio/text to the agency's authorized broadcast system.”

## Tab 3 — Ground Damage Photo Triage

### “Is that result actually from Gemini?”

**If the app shows live confirmation:** “Yes, that specific request returned a Gemini Vision response. The generated observations still require human verification.”

**If it shows offline/fallback:** “No. This is a calibrated benchmark/fallback result, not model output. I will not describe it as Gemini.”

### “Does a configured API key prove Gemini is working?”

“No. The key-presence badge only tells us a value was found. We require a successful request and the live-response indicator; invalid credentials, model access, quota, or networking can still cause fallback.”

### “Why does a sample image produce a convincing incident report offline?”

“The offline benchmark maps known sample filenames to prepared reference triage records. It is for reproducible UI/workflow demonstration. It does not independently inspect or understand the pixels. The current UI labels this as an offline benchmark rather than Gemini output.”

### “Can I upload any disaster image?”

“The interface accepts common image formats. Live interpretation requires a working Gemini credential/network path. Without it, arbitrary images use a generic calibrated fallback; that fallback is not visual recognition and must not guide real operations.”

### “Can the model estimate exact water depth from one photo?”

“Not reliably enough for emergency decisions. A single image lacks scale and sensor context. Any displayed depth is an estimate/model output and requires ground measurements, reference objects, or field confirmation.”

### “What about bias, privacy, or harmful recommendations?”

“Do not upload personally identifiable or sensitive imagery in this demo. A production deployment needs consent/retention policy, restricted access, secure storage, audit logging, bias and robustness evaluation, image provenance, human review, and clear non-authoritative labeling.”

## Tab 4 — Multi-District Risk Matrix

### “Where do the population numbers come from?”

“The district population values are embedded reference values described as Census-era data. They are not real-time population counts, occupancy, or current evacuation numbers.”

### “Are these districts all official coastal districts?”

“The interface uses configured district GeoJSON and fallback lists. A production rollout needs state-authoritative boundaries and an agreed definition of coastal/impact districts; district lists and administrative boundaries change.”

### “What does exporting the CSV do?”

“It downloads the current displayed app data for analysis. It does not publish it, synchronize it to an agency database, or certify the numbers.”

### “Can we audit where every number came from?”

“Today provenance is partly described at the app level, but robust operational auditability is a deployment requirement: each value should carry source, timestamp, version, spatial resolution, transformation, and uncertainty metadata. That is part of the state pilot.”

## Tab 5 — What-If Landfall Simulator / ML

### “What is the model trained on?”

“A 3,600-row synthetic, physics-inspired dataset generated from assumed relationships among surge, elevation, coast distance, wind, rainfall, soil saturation, drainage, and embankment height. These are not 3,600 independently observed storm-damage records.”

### “What does the displayed probability mean?”

“It is the model's score for the configured input profile under the synthetic-data training distribution. It is not a calibrated probability that a specific real road or hospital will fail.”

### “Why quote ROC-AUC above 0.9?”

“Those metrics evaluate separation against labels generated by the synthetic data assumptions. They do not establish real-world predictive performance. We need event-level holdouts and verified post-event damage labels before operational claims.”

### “Is inference in Vertex AI?”

“No. The current model artifact is loaded and inference runs locally in the app process. The Vertex AI manifest/artifact is a deployment-ready blueprint, not a deployed Vertex endpoint.”

### “How should this be validated?”

“With agency-approved event data, event-level rather than random-row splits, leave-one-storm-out testing, calibration and error analysis by state/district, comparison to simple baselines, and shadow-mode tabletop evaluation before any operational reliance.”

### “Do wind and rainfall slider changes update the actual forecast?”

“No. They are hypothetical deltas applied to configured state profiles and passed to the local model. They do not change an IMD or Open-Meteo forecast.”

## Tab 6 — Parametric Insurance Triggers

### “Is this a real policy or guaranteed payout?”

“No. This is a deterministic illustration of parametric trigger logic. It does not represent a contracted insurance policy, insurer underwriting, regulator-approved wording, or any actual payout.”

### “Where do the thresholds and rupee amounts come from?”

“The prototype hard-codes wind/surge tiers, example sums insured, and approximate SDRF corpus assumptions. They are configuration assumptions referencing disaster-risk-financing concepts—not a verified quotation or entitlement.”

### “Who confirms the trigger and sends the money?”

“No external authority, sensor, insurer, or payment processor is connected. The app computes an illustrative result from scenario inputs. A real product needs an insurer, a trusted trigger data source, a contract, fraud controls, governance, and a payment rail.”

### “What does this add to disaster management?”

“It demonstrates how early liquidity might map to thresholds and response needs. The policy and financing design would need legal, actuarial, fiscal, and government review before use.”

## Tab 7 — Real-Time Met Feed

### “Is the weather data live?”

“This tab calls Open-Meteo forecast and marine endpoints. If the result badge says LIVE and shows its retrieval time, those returned weather values are live API data; if it says ESTIMATED, they are fallback values. Always read the badge before making the claim.”

### “Is it the official IMD forecast?”

“No. Open-Meteo is a third-party weather model/API, not an official IMD bulletin. The app maps forecast wind into an IMD-like category label for communication; that label is not an IMD-issued classification.”

### “What location does this forecast represent?”

“The main forecast is requested at configured reference coordinates for the selected state. Marine conditions use an offshore coordinate. The district snapshot code selects the first district row in the current state profile, so I don't describe it as the currently selected inspector district unless I verify that in the UI.”

### “Does the live forecast drive the hazard map, simulator, insurance, or top KPIs?”

“Not in the current wiring shown here. The met tab is a separate live-feed demonstration; the scenario KPIs, simulator, and insurance inputs are derived from the selected historical/configured scenario. Integrating and validating those pipelines is a next step.”

### “How fresh is it?”

“The API provider describes frequent model updates, but this app requests on page render and shows retrieval time; it does not guarantee the underlying forecast model was updated at that exact minute. Always check the retrieval timestamp and source.”

### “What happens if the API is unavailable?”

“The code has a fallback climatological estimate. The source badge should say ESTIMATED; an estimate is not a live observation or forecast.”

“Authoritative data agreements, hydrodynamic validation, real event labels, source freshness indicators, secure secret management, access controls, privacy retention, rate limits, monitoring and alerting, agency approval workflows, fail-safe behavior, accessibility/language review, and controlled disaster-response exercises.”

## Extended Q&A — Technology Stack, Architecture & Scalability

These are additional likely follow-ups if the jury wants to go deeper than the component questions above. Keep the distinction clear between what runs in this prototype and what the proposed production architecture would add.

### Stack and architecture

### “Can you summarize the stack in one sentence?”

“CycloneShield is a Python and Streamlit application using Pandas and NumPy for tabular/scenario processing, Folium for interactive maps, and scikit-learn for local what-if inference, with optional integrations for Gemini, BigQuery, Google Cloud Text-to-Speech, and Open-Meteo.”

### “Why did you choose Python and Streamlit?”

“They let us build and iterate on a data-heavy interactive prototype quickly, using the Python geospatial and machine-learning ecosystem. For a multi-agency production service, we would revisit the UI and service boundaries based on accessibility, security, operational ownership, and measured concurrency requirements rather than assuming Streamlit is the final architecture.”

### “Is this a monolith or microservices?”

“Today it is primarily a single Streamlit application with supporting Python modules. The modules separate concerns such as weather, vision triage, BigQuery, voice, and model inference, but they are not independently deployed microservices. We would split out services only where scale, isolation, ownership, or availability requirements justify the added operational complexity.”

### “What does the request/data flow look like?”

“An operator selects a configured state and storm scenario in the Streamlit UI. The app loads its available historical/configured data, derives screening views, and renders maps and tables. Explicit actions can invoke optional services, such as Gemini image triage; separate tabs can request weather data. The current live-weather tab is not wired into the scenario risk calculations.”

### “What libraries power the main features?”

“Streamlit provides the UI; Pandas and NumPy handle tabular and numerical work; Folium renders map views; and scikit-learn runs the local simulator model. The dependency file also includes geospatial packages and optional Google client libraries. Which external service is actually used still depends on configuration and the visible status for that request.”

### “Is the whole application using Google Cloud?”

“No. It is a Python application and the public demo was hosted on Streamlit Community Cloud. The code includes optional Google integrations and Cloud Run deployment assets, but those do not mean the current demo is running on Google Cloud or that every interaction calls a Google service.”

### “Why not use Vertex AI for inference?”

“The current what-if model is small and runs locally in the app process. Vertex AI is represented by a deployment manifest/blueprint, not a live endpoint. We would consider managed model hosting if validated models, centralized versioning, traffic patterns, monitoring, or deployment governance made it worthwhile.”

### “How are the different services connected?”

“They are optional integration paths called from the application rather than a production message bus or service mesh. The current design favors a reproducible demo and local fallbacks. Production integrations would need explicit service contracts, authentication, timeouts, retries, idempotency, and monitoring.”

### Data and processing

### “Where is the data stored?”

“The prototype reads bundled JSON and GeoJSON files and model artifacts from the repository, with optional external calls. It does not currently provide a production operational database or authoritative multi-agency system of record. A deployed system would need managed, versioned storage with ownership, retention, backup, and provenance controls.”

### “Why use a local cache if NOAA data are available in BigQuery?”

“The bundled historical catalog makes the demo reproducible and usable without credentials or network access. BigQuery is an optional path for querying the public NOAA table. The cache improves demo availability but can be stale; a real deployment needs visible source/version timestamps and a refresh policy.”

### “What happens when an external API is slow or unavailable?”

“Some paths have fallback behavior, such as the cached cyclone catalog or estimated weather values. The operator must rely on the displayed status and source rather than assume the fallback is live data. For production, each integration needs bounded timeouts, retry/backoff rules, circuit breaking where appropriate, clear stale-data warnings, and a tested safe mode.”

### “Are all calculations done in real time?”

“The UI recalculates its scenario views when inputs change, and the local simulator runs in the app process. That does not mean the data are freshly fetched or the underlying hazard model is an operational real-time model. External requests occur only on their specific paths, and their status should be checked.”

### “How do you keep results reproducible?”

“The bundled scenario data and deterministic rule-based views make many demo results repeatable. Production reproducibility would additionally pin data versions, model versions, configuration, code revision, and transformation metadata, and record those with each generated result.”

### “How do you keep data current?”

“There is no general automated authoritative-state-data refresh pipeline in the current demo. NOAA history has a BigQuery query path, while the app also has bundled files. Production freshness requires data-owner agreements, scheduled or event-driven ingestion, validation, versioning, monitoring, and a clear stale-data policy.”

### Scalability and performance

### “What does ‘scalable’ mean in this project?”

“For this prototype, it means the workflow is structured so the same application can be configured for multiple states and scenarios. It is not a demonstrated throughput or user-capacity claim. Operational scale means verified state data, governed integrations, tested performance, and support processes—not just adding more options to a dropdown.”

### “Can it handle thousands of simultaneous users?”

“We have not established that with load testing, so I would not claim a user count. The Cloud Run deployment script is a starting deployment path, not benchmark evidence. We would define realistic workloads, load-test the deployed revision, and tune concurrency, memory, CPU, and service quotas before setting capacity targets.”

### “How would Cloud Run help with scaling?”

“Cloud Run can scale container instances in response to requests, and the repository includes a deployment script with example resource and instance settings. It is not the current hosting environment or a validated production configuration. We would test Streamlit's session behavior, startup time, memory, concurrency, and spend under realistic use before choosing those settings.”

### “What are the likely performance bottlenecks?”

“Likely areas to measure are Streamlit session memory and reruns, loading and rendering geospatial layers, model or image-processing work, and latency or quotas of external APIs. The prototype does not include published load-test results. Profiling and representative load tests should identify which, if any, need caching, asynchronous jobs, or separate services.”

### “How would you scale geospatial processing?”

“First we would benchmark the actual state datasets and map interactions. If data volume required it, we could use spatial indexes and precomputed/versioned hazard overlays or move heavier geospatial jobs into asynchronous workers and managed spatial storage. The present district rows and map layers are not evidence of a production-scale spatial intersection pipeline.”

### “How would you support many users without repeated expensive work?”

“We would cache only results whose inputs and data versions are explicit, with expiration and invalidation rules. User-specific or safety-critical results must not be mixed across sessions. Any cache would expose freshness and provenance, and model outputs would be keyed by the exact model/configuration version.”

### “Would you use a database, queue, or separate workers?”

“The current demo does not need a production database or task queue for its configured workflows. At larger scale, a managed database could hold versioned configurations and audit metadata, while a queue and workers could handle slower ingestion, imagery, or batch geospatial work. Those additions should follow measured needs and agency requirements.”

### “How will you add more states?”

“We would package each state's approved boundaries, storm/data sources, asset definitions, thresholds, language templates, and escalation workflow as a reviewed, versioned configuration. Shared application logic can be reused, but each state must validate its own source data and operating procedures before activation.”

### “How will you add more languages?”

“The interface has seven language choices and prepared broadcast templates. Expanding language support requires translation and terminology review by local speakers, accessibility checks, pronunciation/audio tests, and agency approval. It is not enough to translate labels or rely on an unreviewed machine translation for emergency instructions.”

### “Can states have separate access and data?”

“The current demo is not a multi-tenant agency platform with role-based access controls. A production design would define agency identity, least-privilege roles, state-level data boundaries, audit trails, and approval permissions before onboarding multiple agencies.”

### Reliability, security, and operations

### “What if the internet or power fails during a cyclone?”

“The app has some bundled data and offline fallback paths, but the hosted demo still depends on a working device and network connection. It is not an offline-first field system. A real operational design needs tested low-connectivity behavior, pre-positioned data, resilient hosting, backup power, and a separate communications plan.”

### “How will you monitor the system?”

“The prototype is not a fully instrumented production service. A rollout would monitor availability, latency, errors, resource use, external API status and quotas, data freshness, and model/service versions, while avoiding sensitive content in logs. Operators also need clear incident escalation and status reporting.”

### “How are credentials and sensitive images protected?”

“Keys should be provided through the host's secret manager and never committed or shown. Image uploads may contain sensitive information; production use needs restricted access, transport and storage protections, retention/deletion rules, consent and purpose limits, audit logging, and human review. The competition demo should use non-sensitive sample images.”

### “How do you control cloud and API costs?”

“The prototype has an offline path and a BigQuery dry-run/cost-estimation capability. Production controls would include query byte limits, quotas, caching where safe, API usage budgets, per-service monitoring, and alerting. The current code or deployment assets do not establish a verified per-user cost or free-tier guarantee.”

### “How would you release updates safely?”

“The repository includes container/deployment assets, but the current public demo is not proof of a complete production release pipeline. A production process should add automated tests, dependency and image scanning, staged deployments, health checks, rollback, change approval, and traceability from a release to its configuration and model versions.”

### “What is your scale-up sequence?”

“Start with one state partner and a retrospective validation set; agree on authoritative data and safety gates; test the workflow in a tabletop; then run in shadow mode without driving public decisions. Measure data freshness, false negatives, latency, usability, language quality, and failure behavior. Expand only when the agency signs off on the evidence and operating model.”

## Home-Page Selectors, Displayed Numbers & Source Labels

This section is a practical answer guide for questions about the three top selectors and the provenance strip under the map. Streamlit reruns the app when a selector changes, but that does **not** mean every tab fetches new data or every result is recomputed from live observations.

### “When I change the state dropdown, do all tabs get new state data?”

“Changing state reruns the app and changes the configured district list, cyclone options, state profile, default language, and selected-state weather coordinates. That affects the situation KPIs and map/inspector in Tab 1, the district and state details in Tab 2, the state rows in Tab 4, the state profile in Tab 5, the state-specific insurance assumptions in Tab 6, and the location queried by Tab 7. Tab 3's selected photo/model is a separate triage workflow; changing state does not make that photo state-specific. Tab 8 is an audit/architecture view, not a state data feed. A rerun is not a live refresh of state-owned infrastructure or agency data.”

### “What changes when I select another cyclone?”

“The selected storm changes the map's displayed track when a track is available, headline storm details, and the scenario wind/pressure values. Those values feed the derived surge estimate, district scenario rows and KPIs, alert text, risk-matrix export, and insurance trigger calculation. Tab 7's weather forecast is requested for the selected state's reference coordinates, not from the historical storm track; its separate swell display uses the scenario surge in an amplification illustration. Tab 5 is driven by the selected state's simulator profile and its own sliders, not directly by the selected historical storm. Tab 3 is independent. Historical storm choices are not live forecasts.”

### “What changes when I select a language?”

“The language selector changes the selected-language copy in the broadcast hub and affects the regional voice-broadcast option. It does not translate every dashboard label or every tab: much of the app UI remains English. In the Tab 1 voice panel, English and Hindi are available alongside a regional-language tab; selecting one of the offered regional languages changes that regional option, while English or Hindi leaves the state's regional default in place. The options are implemented templates and voice paths, not proof of reviewed end-to-end translation for every screen.”

### “What does ‘Enter / Upload Custom Live IMD Track’ mean?”

“It opens a form where an operator can upload a CSV track or load a built-in sample. The expected columns are `time`, `lat`, `lon`, `wind_kts`, and `pressure_mb`. A valid uploaded track supplies the positions shown on the map and the peak wind/minimum pressure used in the scenario calculations. It is a manual upload workflow—not a direct, authenticated connection that polls IMD or verifies that a bulletin is current. The sample button is demonstration data. I would call it ‘custom track upload’ unless a real, dated IMD bulletin was supplied and verified.”

### “Is the app scalable beyond seven languages?”

“Yes, seven is the current implemented menu, not a technical maximum. Adding a language means more than adding a dropdown item: we need reviewed emergency-message translations, consistent UI localization, fonts and rendering for the script, text-to-speech availability and pronunciation checks, and approval from the relevant state and language experts. We would add languages incrementally and test safety-critical wording with native speakers.”

### “Are the numbers reliable? If the screen says CRITICAL, how do you derive it?”

“The numbers have different levels of evidence, and the screen should not be read as an operational warning. In the current prototype, the overall storm badge is a rule: CRITICAL/CATASTROPHIC if peak wind is at least 90 knots or the simple surge estimate is at least 3.0 metres; HIGH if wind is at least 64 knots or surge at least 2.0 metres; otherwise MODERATE. District tiers and scores are also generated by deterministic rules based largely on district order in the configured list and the selected wind/surge values. For example, the first listed district is always CRITICAL, and the second becomes CRITICAL at 90 knots. Hospital, shelter, road, and substation impact counts are assigned by those scenario rules, not observed damage or a fresh asset-by-asset flood intersection. ‘CRITICAL’ therefore means ‘prioritize review within this prototype scenario,’ not a verified prediction or an instruction to evacuate.”

### “Can we trust the exact road, hospital, shelter, or population counts?”

“Not as current operational counts. The population values are Census-era references, not current residents or people confirmed exposed. In the dashboard's district table, the facility and road impact values are deterministic scenario outputs; they are not calculated by intersecting a live OSM asset inventory with a validated flood surface. They illustrate the prioritization workflow and must be replaced or validated against current state-owned assets and event observations before operational use.”

### “What does ‘SRTM 30m via OpenTopodata Screening Model’ mean?”

“SRTM is a satellite-derived digital elevation model: a grid of estimated ground elevations. OpenTopodata is an API that can return elevation samples for coordinates. Elevation can support a screening analysis of which low-lying areas might be exposed, but elevation alone does not forecast flood extent; that also needs a defensible water level, hydrology, connectivity, tides, defenses, and validation. Important caveat for this demo: the map's SRTM badge is not evidence that the displayed district scores or road/facility counts were computed from those elevations. The helper in `surge_rain.py` defaults to the `srtm90m` dataset, and the main `app.py` path does not call that elevation helper for the dashboard risk rows. Do not describe the on-screen critical score as an SRTM-derived result.”

### “What does ‘NOAA IBTrACS v4 Real Data’ mean?”

“IBTrACS is NOAA's historical best-track archive: storm observations such as location, time, wind, and pressure compiled for past tropical cyclones. ‘Real Data’ describes the historical source, not a live storm feed. In this app, the track loader checks the bundled local catalog first and uses configured fallback metadata if a track is unavailable; an optional BigQuery path exists. A historical track is useful for replaying a scenario, but it is not a current forecast. For custom upload, the CSV is operator-supplied and is not automatically authenticated as NOAA or IMD data.”

### “What does ‘OSM Overpass Real Data’ mean? Are those counts live?”

“OpenStreetMap is a community-maintained map database, and Overpass is an API for querying it. OSM coverage and tags can be incomplete or out of date, so it still needs ground-truth review for emergency use. Although the repository contains an optional Overpass query helper and an OSM-derived baseline, the main dashboard's risk-row calculation assigns impact counts using deterministic rules; it does not use a successful live Overpass response to calculate those counts. The separate helper defaults to not attempting a live query, and its current loader reads the baseline file. So the provenance pill should not be taken to mean the displayed hospital/road counts were fetched live.”

### “What does ‘Open-Meteo ECMWF IFS Live Feed’ mean?”

“Tab 7 requests a weather forecast from Open-Meteo for configured reference coordinates for the selected state. If the panel says LIVE and gives a retrieval time, the app received an API response for that forecast request; if it says ESTIMATED, it is showing fallback values. It is a forecast, not a weather-station observation or an official IMD bulletin. The code requests Open-Meteo's `best_match` model selection, so the badge alone should not be used to claim that every returned value specifically came from ECMWF IFS. This feed is in a separate tab and does not drive the district-risk KPIs or the what-if model.”

### “So what should we say about the four badges on the map?”

“They describe data sources or intended inputs, not a guarantee that every visible metric was computed from those services during this run. NOAA IBTrACS is a historical source and may be read from a bundled cache. SRTM is elevation data intended for screening, but it does not ground the current dashboard risk rows. OSM is community-mapped infrastructure, but the displayed impact counts are scenario rules rather than live Overpass results. Open-Meteo is a forecast API; check the LIVE/ESTIMATED status in Tab 7 and remember it is not wired into the scenario risk KPIs. I would describe the result as a configured scenario-based screening view and name only the sources actually used.”

## Questions about evidence and claims

### “You showed an estimate as if it were exact. How do we trust it?”

“You should not trust an unqualified point estimate in isolation. The screen is a prototype scenario result. For deployment we would expose source, timestamp, method, confidence/uncertainty, and validation status for each layer, and ask agencies to approve operational thresholds.”

### “Why show simulated data in a competition?”

“It lets judges exercise the workflow reproducibly without relying on external credentials or a current cyclone. The important distinction is explicit labeling: synthetic examples validate the software path, not the real-world forecast accuracy.”

### “What is the next measurable pilot?”

“Pick one state and a retrospective set of named storms. Freeze the data version, compare the system's road/facility risk ranking with verified post-event reports, measure false negatives and alert lead time, review language with local experts, and run a tabletop with duty officers. Only progress to shadow mode if the agency agrees on safety and performance gates.”

### “What's the biggest technical limitation?”

“The most important limitation is validation and data grounding: the current district-impact/risk values are configured screening logic, and the ML model is trained on synthetic scenarios. Operational claims require state-authoritative infrastructure and event-level validation.”

## Presenter answer discipline

1. First answer **what the current demo actually does**.
2. Name its data status: live, historical/cache, configured estimate, or synthetic.
3. Separate the **prototype capability** from the **proposed scale-up**.
4. Do not say “official,” “validated,” “automatically alerts,” “live Gemini,” “Cloud Run deployed,” or “Vertex AI inference” unless the exact live evidence is visible.
5. Keep answers short; invite deeper discussion after the five-minute Q&A slot.
